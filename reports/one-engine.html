One engine

Where the game's architecture should end up once the features settle: one Rust engine, running in the browser offline and inside SpacetimeDB online, with the goal maker, its checks and its benchmark folded in. A plan for review; nothing here is built. It follows the goal spec (drawn) and says where the two disagree.

The end state

One engine crate. Two hosts. The renderer only draws what the engine hands it.

What the engine owns

1
Level generation: the endless board from a seed and density, the home and offline islands, goals (the level maker).
2
Board storage: where every moved block is, indexed by chunk; behind one storage interface with two backends (IndexedDB offline, SpacetimeDB tables online).
3
Moving: an interaction in, the next board state out (and the store updated).
4
View: from a player's location and viewport, the blocks that matter to them, sent to the renderer.
5
Multiplayer: several players and locations, their interactions on one board, who sees what.
6
Islands and offline: the home island, stamped beside the world once online; finishing a goal offline, then the offline island; the outbox replayed on reconnecting.
7
Game features still to come (new block kinds, immovable blocks, goals ending at a place…).
8
Its own checks: cheap assertions that ship (in place of the Referee). Beside it, in the same language but never shipped: the test suite, the benchmarks, and the Records (the fewest moves known for each benchmark goal, to compare against).

The aims, as you put them

  • One engine for offline and online play, never two, so they can't drift apart.
  • Data next to logic. Online, the board's state and the code that changes it live in the same place (a SpacetimeDB module), with no network hop between them.
  • One language for board storage, the level maker, the benchmark harness, and what were the Referee, Judge and Auditor.
  • Fewer moving parts. The Referee, Judge and Auditor may become assertions and unit tests in the engine. The wishes may be hardcoded, to optimise for today's wishes rather than every possible set.
  • No contract between parts. With one engine in one language, it can be optimised as a whole, not just the goal maker.
  • Light on players' devices. Production runs the tuned engine with only cheap assertions; the expensive checks stay in development.

How play flows

Offline

Online, with the client predicting

The server is the authority. The client applies a move at once with the same engine, so the game feels instant through lag. The result comes back the way everyone gets it, through the subscription, the player who moved included; the client then replays its unconfirmed moves on top (client-side prediction and server reconciliation). When the server's board differs, or several moves land at once, one animation moves the blocks to where the server has them; anything else shown (rewards, later) snaps to the server's too.

Islands, offline and back (your design, from TODO.md)

  • A player starts on a home island on the server, cut off from everyone.
  • After some progress, and only while online, it is stamped beside the shared world: an area of any shape (the cells the player touched, plus a margin) that overrides generation there. Online only, so the server places islands so they never overlap.
  • Going offline in the world, the player finishes the current goal; its moves wait in an outbox. Then they carry on on the offline island: in fact a whole endless world with its own seed, called an island because it exists only on the player's device and never touches the online one.
  • Back online, the server replays the outbox through the same engine: the goal's rewards are kept, and the world is rolled back where the moves conflict with what others did meanwhile. The next goal is in the shared world again.
  • Offline play never writes into the shared world beyond one goal, so there is no general merge. (Block positions couldn't be merged freely anyway: a CRDT would give overlapping blocks.)

Why not now

Now: separate parts, a strict contract
  • Features are still being added fast; one tightly optimised engine would make each one harder to add.
  • Goal making is the slowest part, so it is optimised on its own. It needs the Referee and Judge to hill-climb against, and a contract so a maker in another language can be checked.
Later: one engine, no contract
  • Once the maker sits in a local minimum, the gains are across the whole system (storage, moves, view, maker together), and a contract between them gets in the way.
  • Once the features settle, the engine's shape can be fixed and ported once.

Decided

  • Server time. The next goal is made in the blocking reducer, as the player pushes the red block onto its target (a few ms; the push animation hides it and the network). Other players wait those few ms, in exchange for no consistency issues.
  • Memory. It grows with the number of players. The board is a table like everything else in SpacetimeDB, which manages memory and storage; the rule is to use SpacetimeDB the intended way.
  • The server is the authority. A missed prediction, or several moves landing at once (a lag spike, a replayed outbox), uses one animation to the server's board; rewards snap to the server's too.
  • Testable all the way. The default path, prediction, failures, replays and their animations, in deterministic simulation tests (TODO.md: a seeded simulated network and clock).
  • The port. Checked against today's implementation while porting, then the comparison goes.

Open

  • Online to offline and back. The one place the player jumps. The direction: while the last online goal is played (the player already offline), zooming out still shows the whole online world; when that goal is finished, the camera pans to the offline world, its blocks turning from online to offline blocks on the way; landed and zoomed out, the whole endless world is the offline one. Back online, the same the other way. The details are found by building it, not specified ahead.
  • Stamping islands. Where each home island goes beside the world. To design together, when it is built.
